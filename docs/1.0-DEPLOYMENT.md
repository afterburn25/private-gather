# 1.0 Deployment Guide

## Initial demo target

The current test installation is:

`https://demo.privoralabs.com/private-gather/`

Private Gather supports both document-root and subdirectory mounting. For a subdirectory deployment, extract the package into that application directory (for example `private-gather/`). Do not point the URL at a nested `/public` directory and do not expose Laravel internal folders directly.

## Fresh installation

1. Create the subdomain/document root.
2. Create an empty MySQL/MariaDB database and database user, or give the installer credentials that are permitted to create the selected database.
3. Prepare PHP dependencies. The source ZIP intentionally does not contain Composer `vendor/` dependencies. Run `composer install --no-dev --optimize-autoloader` in the release tree (on the server or a compatible build machine), then upload/include the resulting `vendor/` directory. The browser installer will not proceed without `vendor/autoload.php`.
4. Upload/extract the prepared 1.0 release into the intended application directory (document root or subdirectory).
5. Ensure `storage/` and `bootstrap/cache/` are writable by PHP.
6. Confirm the required PHP extensions are enabled.
7. Visit the application URL, for example `https://demo.privoralabs.com/private-gather/`.
8. The pre-install front controller renders the installer inline at that same application URL and must not redirect to domain-root `/install/`.
9. Enter application, database, administrator, and domain settings.
10. The installer generates `.env`, imports the complete schema, records all baseline migrations, creates the first platform administrator, writes a private install record/lock, clears caches where possible, and removes or disables the installer directory.
11. Reopen the application URL. The application must load normally and remain at the configured mount path.
12. Sign in at `/admin/login` and open System Health.

## Platform subdomains

To give tenants hostnames such as:

`sunset.demo.privoralabs.com`

configure wildcard DNS for the platform root, for example conceptually:

`*.demo.privoralabs.com -> the same public web edge/origin`

The web server/reverse proxy must accept wildcard tenant hostnames and send them to this application. The TLS layer must also cover those hostnames (for example with an appropriate wildcard certificate or automated edge certificate solution).

`PLATFORM_ROOT_DOMAIN` controls the domain suffix used by tenant provisioning. For this test deployment, use:

`PLATFORM_ROOT_DOMAIN=demo.privoralabs.com`

## Customer-owned custom domains

A client may attach `clubname.com` or `events.clubname.com`. The application stores that hostname, generates an ownership-verification token, and resolves the tenant from the incoming Host header after activation.

The bundled 1.0 domain layer is provider-neutral. Infrastructure must still route each verified custom hostname to the application and obtain/renew HTTPS certificates. A later provider adapter can automate this through an edge service such as Caddy/ACME or a SaaS-domain provider without changing tenant/event data.

Never use iframe masking or registrar HTTP forwarding for a real custom domain. DNS/TLS should terminate at the platform so the client's domain remains visible for every page.

## Background work

The default installation uses the database queue. Production deployments should run a queue worker for mail/notifications and scheduled work. Configure the host's process supervisor or equivalent to keep the worker running.

## Email

Fresh installs default to the log mailer so installation does not fail when SMTP is unavailable. Configure a real transactional mail service before relying on email verification, password resets, event notices, or organizer communications.

## Payments

1.0 includes the payment abstraction, orders, payment records, and a manual/offline gateway. It deliberately does not embed processor credentials. Before enabling real online payments, integrate a provider that explicitly supports the business model and configure webhooks/idempotency/refunds for that adapter.

## File/media storage

Local storage is suitable for the demo. For scale, use private S3-compatible object storage/CDN and keep privacy-restricted media behind authorization rather than directly exposing raw files.

## Upgrade Center

After the initial installation, use `/admin/upgrades` instead of manually copying application files. Upgrade ZIPs are source-version locked and contain:

- `manifest.json`
- `payload/VERSION`
- changed/new files
- versioned Laravel migrations where required

The updater validates hashes, creates file backups, enters maintenance mode, snapshots the database when tooling is available, runs migrations, replaces/deletes declared files, clears caches, records the result, and returns the application online.


## Private Gather production identity

The production brand domain is `privategather.com`. The initial certification environment may use `demo.privoralabs.com`; the browser installer auto-detects that hostname so tenant test subdomains can be created beneath the demo root without changing the production brand identity.
